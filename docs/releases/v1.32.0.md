# Chatbox Venice 1.32.0

Venice privacy can now be configured for each conversation. Existing chats continue to inherit the provider settings until explicitly customized.

- In **Conversation Settings → Venice privacy for this chat**, keep **Use provider privacy defaults** on, or turn it off to choose HTTPS, TEE or E2EE, receipt verification and encrypted-tool permissions for that chat. Changes do not affect the provider or other chats. Returning to inheritance follows the provider defaults again.
- Lowering transport protection requires confirmation. An incompatible model shows a warning and is rejected before an inference request; the app never silently falls back to plaintext. The provider Privacy Only catalog restriction remains in force.
- Receipt compatibility and encrypted/native tool consent retain their separate warnings. Model/search profiles and vendor request JSON cannot grant these permissions. Search and Work/MCP capability controls refresh when a chat privacy setting changes, including new-chat drafts.
- The UI distinguishes encryption from response verification and explains the remaining reliance on Venice for model hardware verification. Hardware authenticity, approved software measurements and exact payload binding are distinct guarantees.

## Live receipt investigation

Fresh short text probes reproduced request/response body-hash mismatches on Qwen/Phala and DeepSeek/NEAR, with both streamed and buffered E2EE responses. Qwen TEE-only probes had the same mismatch. The exact 1.31.0 release transport rejected Qwen and DeepSeek in strict mode and completed encrypted text in compatible mode. A modified Gemma ciphertext and a wrong recipient key were both rejected locally.

The independent [venice-e2ee receipt verifier](https://github.com/elkimek/venice-e2ee/blob/main/src/receipt.ts) documents the same public-API body-binding limitation. This is not proof of malicious response alteration or a full reconstruction of every gateway rewrite. Compatible receipts remain opt-in and provide less assurance than independently matching the signed payload. Strict live payload binding is still unresolved; no normalization, automatic fallback or paid retry has been introduced. See [the detailed policy and investigation](https://github.com/n3me5is-git/chatbox-venice/blob/main/docs/venice-secure-receipts.md).

## Validation

Actions check TypeScript, profile/schema persistence, incompatible-model rejection, chat isolation, tool capability refresh, React controls and mobile Chromium touch interaction. English and Italian strings are explicit; other languages retain English fallback. API probes used the authorized temporary key in a local process only; it was not stored or supplied to Actions. These probes do not verify every model or independently certify model GPU evidence and software provenance. Existing Android biometric fixes and signing identity are retained.
