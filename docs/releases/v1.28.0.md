# Chatbox Venice 1.28.0

Adds encrypted local media storage, app/project access protection and model-aware Venice editing, while retaining existing Chatbox providers and workflows.

## Local storage, access and cleanup

- New native media uses authenticated encrypted chunks with device-protected keys. History loads small thumbnails and selected previews instead of eagerly loading every video/audio file. New native transcripts are encrypted text files, and native media export streams without opening a preview first.
- Data & Backup adds public/protected library sections, file sizes, selected deletion, incomplete-download cleanup, verified legacy-media migration and portable encrypted library backup/restore.
- PIN/passphrase and biometric/device unlock can be enabled independently. App-open and background locking have separate switches. Windows uses DPAPI plus a native Windows Hello access gate; Android uses Keystore and strong-biometric key operations.
- Projects can use app unlock or their own PIN. Locked projects guard chat access and library attachment selection; drafts/private prompt history are isolated. New Venice tool outputs inherit their project's media protection.
- Image/Studio sessions can be protected, including prompts and generation metadata. Locking closes private previews/dialogs and stops local generation/polling.
- Chats can be deleted directly after confirmation. Image cleanup includes thumbnails and local-edit resources.

Project locks protect access inside the app; existing ordinary chat databases, settings and external Work Mode files are not encrypted by that switch. Public native media still uses device encryption. Library backups restore media/library metadata, not Studio/image workflow history or conversations; conversation backup remains separate.

## Venice capabilities

- Optional TEE verification and text E2EE with fail-closed signature/attestation checks. Privacy Only restricts models to Private or TEE/E2EE capabilities. Hardware certificate verification relies on Venice's reported verdicts, not an independent Intel/NVIDIA root-chain verifier.
- Catalog-driven privacy/anonymous/uncensored badges and “Show other models from Venice” across model types.
- Separate music and sound effects. Voice cloning and dedicated voice conversion include compatible file/voice controls, local recording, duration preflight and conversion quotes.
- Device upload or existing local media selection in attachment controls.
- Remix/edit offers compatible model selection, source/batch controls and percentage comment points. Painted-area edits send a context crop to Venice and apply the mask locally; no unsupported mask parameter is sent. Local editing supports PNG/JPEG/WebP up to 8 megapixels.
- Voice-clone handles can be removed locally; server-side samples follow Venice's retention period. Immediate remote sample deletion is not claimed.

E2EE applies to compatible text chat and disables attachments/tools/search; image/media APIs use HTTPS. Paid requests are not automatically replayed after errors.

## Verification and installation

GitHub checks cover TypeScript, cryptographic tampering/truncation, PIN/device-key lifecycle, project boundaries, migration, backup restore, media/API serialization and UI regressions. Chromium exercises mobile/desktop interactions, masked pixel composition, model filtering, comment points, PIN rejection and independent unlock settings without paid API calls. Separate native checks compile the Windows Hello helper and Android Keystore/biometric plugin.

Simulated device unlock is not a physical biometric test. Real Venice inference, device enrollment, codecs/microphone permissions and installation need checking on the target device. See [testing](https://github.com/n3me5is-git/chatbox-venice/blob/main/docs/fork-testing.md) and [local protection](https://github.com/n3me5is-git/chatbox-venice/blob/main/docs/local-security.md).

Download this fork's Windows x64 setup or signed Android APK from this release. Android retains the pinned identity configured in private Actions Secrets. No Google Play account is needed to produce the packages; device-specific installation rules still apply. Windows installers remain unsigned.
