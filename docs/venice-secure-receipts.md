# Venice E2EE gateway receipts

## What the live investigation found

Venice's public API and the attested inference gateway are different byte boundaries. The gateway uses upstream model identifiers, records request transformations, and returns a response that Venice can decorate with model/usage metadata. A signature over gateway-observed request/response bytes cannot be assumed to hash the outer JSON/SSE received by this app. JSON key sorting is not a documented repair: these are SHA-256 hashes of bytes, not a canonical JSON signature.

Live calls on November 6, 2026 established that decryption succeeded and the EIP-191 signature recovered the same secp256k1 address bound into the fresh TDX attestation. The signed request/response hashes did not match the app's exact request and response bytes. The API's signature response explicitly instructs clients to treat its hashes as provider-reported unless a documented canonical representation can be independently reconstructed. This is an interoperability boundary, not evidence of a wrong signer.

The current [Venice response-signature guide](https://docs.venice.ai/guides/features/tee-e2ee-models#response-signatures) describes checking the signer against the attestation. The [Phala ACI specification](https://github.com/Phala-Network/private-ai-gateway-with-vllm-router-as-middleware/blob/main/spec/aci.md) distinguishes received/forwarded request bytes and cleartext/wire response hashes. Its [receipt builder](https://github.com/Phala-Network/private-ai-gateway-with-vllm-router-as-middleware/blob/main/src/aci/receipt.rs) hashes exact bytes. The live legacy surface still supplied `response.returned.body_hash`, whereas the current ACI specification uses `wire_hash` and `cleartext_hash`.

We also reviewed the current [venice-e2ee receipt verifier](https://github.com/elkimek/venice-e2ee/blob/main/src/receipt.ts). Its full ACI verification requires an independently established workload-keyset trust anchor and exact request/response bodies. The compatibility quote binds the legacy E2EE key and nonce; copying an Ed25519 key from unauthenticated metadata would not establish that additional trust. This app does not claim full independent ACI verification or invent normalizations until a hash happens to match.

A second implementation issue was the zero-padded quote transport used by Phala and NEAR AI. The client now accepts at most 256 trailing zero bytes only for those providers' TDX v4/type 0x81, then parses the declared quote length strictly. Nonzero/excess padding and other providers remain rejected.

## Choose the verification policy

Strict payload binding has not yet passed a live Venice call in this fork. Passing synthetic enclave tests does not establish live gateway interoperability. New direct probes on November 7 reproduced body-hash mismatches with Qwen/Phala and DeepSeek/NEAR in buffered and streamed E2EE responses, and with Qwen/Phala in TEE-only mode. An independent implementation records the same limitation in its [receipt verifier](https://github.com/elkimek/venice-e2ee/blob/main/src/receipt.ts): the public Venice API has a reserializing hop outside the receipt's byte boundary. This is evidence of an interface boundary, not proof that every individual byte transformation has been reconstructed or that the service maliciously altered a response. The legacy signature endpoint itself says to treat hashes as provider-reported unless independently reproducible. No automatic normalization or weaker fallback is used.

In **Settings → Providers → Venice**, choose **Secure text chat → Require end-to-end encryption**. **Compatible gateway receipts** is off by default. Enabling it opens a separate warning and requires confirmation. Provider settings supply defaults. Dedicated **Conversation Settings → Venice privacy for this chat** controls can explicitly override transport, receipt compatibility and tool consent for one chat. Model/search profiles, extra request JSON and tool output cannot enable them. Turning off provider inheritance snapshots the current defaults; restoring inheritance follows subsequent provider changes. Switching to weaker transport requires a separate confirmation. The provider Privacy Only catalog restriction still applies.

- **Default strict E2EE verification:** requires the attested signature to bind the exact request and received content. Native tool calls additionally require coverage of their actual arguments. The live gateway mismatch withholds output and offers no plaintext retry.
- **Explicit compatibility:** keeps fresh attestation, model/key/nonce checks, encrypted input/output, AES-GCM authentication and the signature from the attested key. For Phala ACI receipts it checks the version, request/receipt identifiers, endpoint and consistency between signed hashes and receipt events. For NEAR gateway signatures it checks the signature kind, requested completion ID and separately attested gateway identity. It trusts the provider-reported hashes rather than proving their independent binding to the app's actual payload. Substitution or replay of a payload may therefore escape this check. The active setting shows this limitation persistently.

This limitation also applies to tool selection. Encrypted tool messages keep definitions/calls/results inside encrypted text; native tool envelopes remain visible to Venice after separate consent. Both use the selected receipt policy plus existing SDK schema checks and tool/media approvals. Search and external MCP services receive execution arguments regardless of the model transport.

No verification failure silently enables compatibility, sends a plaintext prompt, or repeats a paid completion. Switching compatibility off restores strict verification immediately for subsequent requests. The transport marks released responses internally as `payload-bound` or `gateway-signature-only`; it does not label the latter as independently authenticated payloads.

## Live verification

The production transport completed an E2EE text call with Qwen and a full encrypted-text tool cycle with Gemma: the model selected `local_sum(7,5)`, the local tool executed once, and the result returned to the model encrypted before the final answer `12`. These calls used explicit compatible receipts. Qwen's smaller model also executed the tool, but produced an additional invalid call handled by SDK validation; model instruction-following is distinct from transport verification. A further full encrypted-text tool cycle passed on NEAR/DeepSeek V4 Flash, including two fresh model attestations, two signatures and independently verified gateway quotes. An E2EE Brave search then executed exactly one `/augment/search` request, returned HTTP 200 and produced a linked source in the final answer. This is not certification of every catalog model. Model hardware verification still relies on Venice; the separate NEAR gateway CPU quote is verified locally against Intel roots.


## NEAR model and gateway signing keys

The [official NEAR verification example](https://github.com/near-examples/nearai-cloud-verification-example#-signature-kinds) distinguishes `provider_tee` signatures from `gateway` signatures. Streaming responses are signed by the gateway. The live Venice attestation returned the model encryption/signing identity, while `/tee/signature` correctly returned the different gateway signing identity. Reusing the model key for that signature was a client implementation error.

The app now fetches a fresh public report from the fixed `https://cloud-api.near.ai/v1/attestation/report` endpoint without sending a Venice API key, prompt or media. It checks `gateway_attestation`, the exact expected signing address, nonce, REPORTDATA binding and debug flag. It then verifies the separate gateway quote with the pinned pure-JavaScript `@phala/dcap-qvl` 0.7.1 verifier, using Intel-rooted collateral from `https://pccs.phala.network`. Only `UpToDate` is accepted. The model encryption key is unchanged. The model GPU verdict is not reused for the gateway, which has a CPU-only quote.

The gateway key was validated live with Intel-chain verification. Browser CI additionally uses a public quote/collateral fixture at a fixed verification time, verifies it with the actual browser crypto implementation and rejects a modified quote, without external requests. Neither software measurements nor container/model provenance are allowlisted by this app. The gateway-identity correction does not repair the independent payload-hash boundary, so explicit compatible receipts are still needed where Venice rewrites the gateway wire.

Native tools remain model/gateway-dependent. The tested DeepSeek model accepted the encrypted request and signed reply in native mode but answered directly without a tool call. The encrypted-text protocol completed the tool round trip on that same model. No automatic transport switch occurs.

The exact 0.7.1 verifier includes the upstream TCB/QE collateral-signer security restriction. Its six-line verification change and upstream regression test were reviewed against 0.7.0. This package alone has a documented minimum-release-age exception; other dependency-age and script restrictions remain in force. Browser tests also reject a PCK certificate chain substituted for either collateral signer.
